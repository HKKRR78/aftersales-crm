# 售后经营平台重构需求文档（v0 使用）

> 文档版本：v0.1
>
> 编写日期：2026-09-18（Asia/Shanghai）
>
> 用途：作为 v0 生成前端页面、交互原型和 API 对接边界的唯一输入之一。
>
> 当前状态：需求整理稿，不代表 Hono 服务、PostgreSQL 数据库、同步定时器或生产补数已经完成。

## 1. 一句话定义

建设一个“有来源、有证据、有批次、有更新时间”的售后经营数据平台：把公司服务器外部数据库、班牛 API 和新工单系统的数据统一采集到 PostgreSQL，经业务模型和质量检查形成可供前端直接读取的业务数据，再由 Hono.js 提供页面 API。

前端不能直接查询原始数据表、班牛表、新工单表或订单大表；前端只读取经过发布的数据集和业务查询接口。

## 2. 交付背景与本次目标

当前交付时间紧张，目标是在下周一（2026-09-21）前形成可以演示、可以继续接真实数据的第一版。

本次不是继续在旧数据链路上零散修补，而是先完成以下边界划分：

1. 明确三个数据源及其责任边界。
2. 统一班牛历史数据和新工单数据，使它们可以在同一个售后业务模型中展示。
3. 设计独立的同步任务、批次、日志和质量检查机制。
4. 使用 PostgreSQL 业务表/读模型承载前端展示，不让页面依赖源表结构。
5. 为每一笔工单保留可追溯的来源证据。
6. 先补齐本周数据，再按同样方法向前补齐上一周及更早的必要周期。
7. 使用 Hono.js 提供稳定、清晰、可验证的页面 API。

## 3. 已有项目基线（必须保留的业务含义）

当前仓库是 `HKKRR78/aftersales-crm`，已有前端使用 Next.js 16、React 19、TypeScript，当前页面和业务含义如下。v0 可以重新设计视觉和信息层级，但不能无故丢失这些核心能力。

| 当前页面 | 现有能力 | v0 处理方式 |
| --- | --- | --- |
| 经营总览 | 全量售后问题、经营异常、产品销量、售后率、周环比、五周趋势 | 保留为首页主工作台，并增加数据来源、批次和新鲜度信息 |
| 问题明细 | 按产品、商品链接、一级/二级/三级问题、仓库和预警筛选 | 改为大数据量问题工作台，支持分页、筛选、详情抽屉和证据追溯 |
| 产品周报 | 按售后创建周查看有问题产品，待匹配记录单独提示 | 保留，并显示来源构成和补数状态 |
| 仓库分析 | 只统计库房问题，按仓库问题数和订单分母分析 | 保留，并增加仓库映射置信度和待映射提示 |
| 规则设置 | 管理五大问题分类和可剔除规则 | 保留管理员入口，规则变更必须形成版本和审计记录 |
| Excel 导出 | 导出经营分析、问题、产品和仓库结果 | 作为现有能力保留，接口迁移到 Hono 后保持筛选口径一致 |

当前已确认的核心问题分类为：快递问题、库房问题、买家问题、产品问题、运营问题。未归入五类的问题必须显示“待归类”，不能静默归入其他类别，也不能在数据不完整时伪造 0。

当前可确认的访问角色只有 `admin` 和 `viewer`。v0 不自行增加客服、仓库、商品等业务角色；业务职责分工需要后续由用户确认。

## 4. 目标架构

### 4.1 分层关系

```text
外部数据源
  ├─ 公司服务器外部数据库（CRM 之外的数据，例如光电通及其他来源）
  ├─ 班牛 API（历史/旧体系）
  └─ 新工单系统 API（新体系）
          │
          ▼
采集与同步任务
  ├─ 定时同步
  ├─ 指定日期范围补数
  ├─ 分页完整性检查
  ├─ 幂等写入
  ├─ 批次与日志
  └─ 每笔工单来源证据
          │
          ▼
PostgreSQL（部署在 autorpc，具体连接参数由部署环境提供）
  ├─ 原始层：保留来源原文和摘要
  ├─ 统一事实层：班牛与新工单统一为售后事实
  ├─ 业务层：面向前端的工单、商品、仓库、指标模型
  ├─ 数据集版本：决定哪个批次可以被页面读取
  └─ 运行与质量层：同步运行、日志、证据、检查结果
          │
          ▼
Hono.js API
          │
          ▼
Next.js / v0 前端页面
```

### 4.2 技术约束

- 新的数据服务使用 Hono.js + TypeScript。
- 新的持久化数据库使用 PostgreSQL，不使用 MySQL。
- 页面 API 不在请求期间直接访问班牛 API、新工单 API 或源数据库。
- 页面 API 只读业务层/发布数据集；原始层只能通过审计或工单详情接口间接查看。
- 同步任务和页面请求分离。请求超时、外部 API 不可用或同步失败时，不能阻塞页面服务。
- 不在 Hono 请求中临时启动一轮全量采集。
- 定时器必须有明确的唯一归属。若现有 autorpc 已承担采集中心和调度，应复用该调度能力；不要因为 Hono 接页面又复制一套互相竞争的调度器。
- 所有时间以 `Asia/Shanghai` 解释和展示；数据库中建议保存带时区时间。
- 所有外部副作用按“至少一次执行”设计，使用稳定业务键、唯一约束、结果查询和未知状态处理，不能假设网络重试天然只执行一次。

## 5. 数据源边界与兼容规则

### 5.1 三个数据源

| 数据源 | 业务定位 | 进入系统的方式 | 必须保留的信息 |
| --- | --- | --- | --- |
| 公司服务器外部数据库 | CRM 之外的基础资料、订单/商品/仓库等辅助事实，例如光电通或其他来源 | 只读连接或受控同步任务 | 数据库/表来源、读取窗口、读取时间、批次、行数、摘要 |
| 班牛 API | 旧体系、历史售后记录 | 分页 API 同步及历史补数 | 班牛任务 ID、子商品行键、API 请求窗口、分页证据、原始响应摘要 |
| 新工单系统 API | 新体系、交接后的售后工单 | 分段读取、完整性双读、定时同步 | 新工单 ID、商品行、创建/修改时间、覆盖范围、分页摘要、原始 JSON |

### 5.2 班牛与新工单的统一规则

- 两个来源必须保留 `source_system`，不能把来源名称抹平。
- 统一事实表提供平台无关的公共字段；来源特有字段放在 `source_payload` 或来源扩展表中。
- 工单和商品行分别建模：一个工单可以有多个商品/问题行。
- 业务唯一键必须由来源稳定 ID 和商品行标识组成；不得用商品标题作为主键。
- 同一个来源的重复读取必须幂等；跨来源疑似重复只能标记供人工确认，不能未经确认自动合并。
- 班牛和新工单交界日期/时间必须是可配置的 `cutover_at`，不得写死在页面代码中。
- 交界前以班牛记录为旧体系，交界后以新工单记录为新体系；交界批次必须输出两边的数量、重叠、缺失和疑似重复对账结果。
- 任何来源记录从接口消失、分页摘要变化、分页重复或覆盖范围不完整时，批次不能发布为页面数据。

### 5.3 最小统一字段

以下字段用于支撑 v0 页面；没有值时必须保留空值和缺失原因，不使用猜测值：

- 工单：`ticket_id`、`source_system`、`source_ticket_id`、`business_key`、`shop_name`、`status`、`created_at`、`updated_at`。
- 商品行：`ticket_item_id`、`source_item_id`、`order_id`、`sub_order_id`、`merchant_code`、`product_id`、`product_title`、`sku_text`、`quantity`。
- 问题：`p1`、`p2`、`p3`、`category`、`classification_status`、`included_in_operating`。
- 物流/仓库：`tracking_no`、`carrier_name`、`warehouse_code`、`warehouse_name`、`warehouse_match_status`。
- 金额/时间：`after_sales_amount`、`refund_amount`、`payment_at`、`refund_requested_at`。
- 追溯：`source_run_id`、`evidence_id`、`raw_record_id`、`observed_at`。

商品标题只能用于展示和搜索，不能替代商家编码、商品 ID 或业务唯一键。

## 6. PostgreSQL 业务模型要求

最终可以拆成多张表，但必须以“前端所需业务数据可直接读取”为目标设计，不让页面每次临时拼接多张源表。

### 6.1 原始与证据层

建议至少包含：

- `source_records`：来源系统、来源记录 ID、原始 JSONB、内容哈希、首次观察时间、最后观察时间。
- `source_evidences`：证据 ID、来源系统、来源记录/工单 ID、同步运行 ID、读取窗口、请求/页面定位信息、内容哈希、采集时间。
- `sync_runs`：同步任务、来源、触发方式、时间窗口、状态、开始/结束时间、读取数、写入数、更新数、跳过数、错误码、错误摘要、批次摘要。
- `sync_run_pages`：分页序号、请求参数摘要、响应摘要、读取行数、重复数、是否完整。
- `system_logs` 或结构化日志索引：任务事件、级别、运行 ID、工单/业务键、消息和错误堆栈。

每一笔工单至少能反查到：来源系统 → 来源 ID → 同步批次 → 原始记录/内容哈希 → 采集时间。

### 6.2 统一事实层

建议至少包含：

- `after_sales_tickets`：统一工单主记录。
- `after_sales_ticket_items`：工单下的商品/订单行。
- `after_sales_issue_facts`：问题路径、问题分类、经营统计状态和相关商品/仓库。
- `products`：商家编码、商品 ID、展示名称和来源关联，不以标题做唯一键。
- `warehouses` 与 `warehouse_mappings`：仓库编码、名称、来源、匹配方式、置信度和人工确认状态。
- `order_facts`：全店、商家编码、商品、仓库等粒度的订单数和销量，用于分母，不把售后行购买数当成销售分母。

### 6.3 业务读模型/汇总层

为前端直接读取，建议提供以下读模型：

- `business_overview_daily` / `business_overview_weekly`：首页 KPI 和趋势。
- `business_issue_summary`：问题分类、商品、仓库和周期聚合。
- `business_product_weekly`：产品周报及待匹配数量。
- `business_ticket_detail`：工单详情、处理信息、证据摘要。
- `analytics_dataset_versions`：可供页面使用的已发布数据集版本。
- `analytics_quality_checks`：该版本通过的覆盖、分页、重复、订单水位和新鲜度检查。

页面只读取最近一个 `published` 且通过必需质量检查的数据集。新批次失败时保留上一版完整数据，并在页面明确显示“数据未更新/使用上一版”。

## 7. 同步、定时器与补数

### 7.1 同步任务

同步任务按来源拆分，至少有：

1. 外部数据库辅助数据同步。
2. 班牛增量同步。
3. 新工单增量同步。
4. 订单/商品/仓库补全同步。
5. 业务读模型计算与数据集发布。
6. 质量检查与运行汇总。

每个任务必须可以独立成功、独立失败和独立补跑；一个来源失败不能悄悄阻断其他已经独立完成的来源。

### 7.2 日更/周更判断

系统需要先观察每个数据源实际更新时间，再决定调度频率，不能凭感觉设为“每天”或“每周”。

- 日更来源：在源数据稳定产生后的固定时间读取上一完整日，并记录实际源更新时间。
- 周更来源：在周一报表截止前完成上一完整周，默认必须在周一 15:00 前形成可读的已发布数据集。
- 如果源数据在周一 15:00 前仍未完整，页面必须显示“数据未完成”，不能显示 0 或伪造完成状态。
- 调度任务必须保存计划时间、实际开始/结束时间、数据窗口和最终状态。
- 定时器应调用同步任务，而不是直接修改业务表；业务表更新必须经过批次、校验和发布门槛。

### 7.3 补数顺序

第一阶段按以下顺序执行：

1. 先补齐当前周，验证当前周的数量、来源、问题分类、商品/仓库关联和页面结果。
2. 当前周通过后，按相同规则补上一周。
3. 再向更早周期推进，优先覆盖首页趋势、产品周报和业务需要的比较周期。
4. 如果某一周正好跨越班牛与新工单的交界，使用两来源对账后的差异/减法结果，避免把两个体系整段重复录入。

补数必须先支持 `preview/dry-run`：输出新增、更新、未变化、缺失、重复、疑似跨来源重复和无法匹配的数量；人工确认后才允许写入并发布。

### 7.4 幂等与重试

- 同一来源、同一业务键、同一输入内容重复读取不产生重复工单。
- 只重试失败的可验证单元，例如“来源 + 日期窗口”“来源 + 页码”“店铺 + 时间段”或“工单 + 商品行”。
- 外部请求超时但结果未知时，先查询结果或重新核对，不直接盲目重放。
- 每次运行有统一重试预算和最终状态：`pending`、`running`、`succeeded`、`partial`、`failed`、`unknown`。

## 8. Hono.js API 需求

### 8.1 通用约定

- 前缀统一为 `/api/v1`。
- 成功响应建议统一为 `{ data, meta }`；失败响应为 `{ error: { code, message, details } }`。
- 列表接口必须返回 `items`、`total`、`offset`/`limit` 或 cursor、`datasetVersion`、`generatedAt`。
- API 必须支持 `datasetVersion` 或 `batchId`，以便页面和导出使用同一份事实。
- 分页、筛选、排序都在服务端执行；禁止把全部历史数据一次性塞进首屏。
- 所有指标同时返回状态：`ready`、`partial`、`stale`、`unavailable`。数值未知时返回 `null`，前端展示 `—`。
- 所有查询接口记录请求 ID、用户 ID、数据集版本、耗时和错误信息。

### 8.2 页面读取接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/healthz` | 进程存活检查，不依赖业务登录 |
| GET | `/readyz` | PostgreSQL、数据集、新鲜度和必要质量检查 |
| GET | `/api/v1/overview` | 首页 KPI、当前周期、趋势、来源状态和数据集信息 |
| GET | `/api/v1/issues` | 问题工作台分页查询；支持周期、来源、商品、问题路径、仓库、状态和关键词 |
| GET | `/api/v1/issues/:id` | 单条问题/工单详情，包含来源证据摘要和原始记录定位 |
| GET | `/api/v1/products/weekly` | 产品周报、可选周、待匹配数、周环比 |
| GET | `/api/v1/warehouses` | 仓库问题汇总、订单分母、映射状态和下钻入口 |
| GET | `/api/v1/rules` | 五大分类及可剔除规则 |
| GET | `/api/v1/data-status` | 当前发布版本、各来源最新同步、数据窗口、质量检查和滞后原因 |
| GET | `/api/v1/sync/runs` | 同步任务运行列表、过滤来源/时间/状态 |
| GET | `/api/v1/sync/runs/:runId` | 单次运行详情、分页证据、错误和影响范围 |
| GET | `/api/v1/export` | 按页面筛选条件导出业务数据，必须与页面同一数据集版本 |

### 8.3 管理与内部任务接口

以下接口默认只允许内部任务或管理员调用，不直接暴露给普通 viewer：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/internal/sync/:source` | 执行指定来源的增量/指定窗口同步 |
| POST | `/internal/backfill/preview` | 补数预演，返回差异和质量摘要 |
| POST | `/internal/backfill/apply` | 应用已确认的补数批次 |
| POST | `/internal/datasets/:id/publish` | 通过质量门槛后发布业务数据集 |
| PATCH | `/api/v1/rules/:ruleId` | 管理员修改确认过的规则，并产生审计记录 |

Hono 服务不负责替代已有采集中心的浏览器登录、验证码处理或调度注册；这些属于数据采集执行器边界。Hono 负责统一读模型 API、任务状态和页面所需的管理接口。

## 9. v0 前端页面需求（给 v0 的直接提示）

### 9.1 总体视觉和布局

请生成一个中文企业内部售后经营平台，风格为“安静、可信、数据密度高但不拥挤”，延续榆园品牌的深绿色、浅灰绿色背景、白色卡片和少量浅黄/红色状态色。

- 左侧固定导航：经营总览、问题工作台、产品周报、仓库分析、同步与数据质量、规则设置。
- 顶部显示当前用户、角色、当前数据集版本、最后更新时间和数据状态。
- 页面优先桌面端，同时适配平板和手机；大表格使用服务端分页/虚拟滚动。
- 页面所有空值、未知分母、未完成补数和跨来源待对账状态都要有明确文案。
- 不要生成营销型 Landing Page，不要使用虚构的实时大屏、炫目的渐变和无业务含义的图表。

### 9.2 经营总览

首屏展示：

- 全量售后问题数。
- 经营异常问题数。
- 销售订单数和产品销量。
- 经营异常售后率。
- 相对上一个完整周期的变化。
- 数据更新时间、当前数据窗口、数据集版本和各来源构成。

中部展示：

- 最近五个完整周趋势。
- 当前周同进度视图，可切换“完整周/本周进度”。
- 五大问题分类分布和待归类数量。
- 产品预警榜。
- 仓库风险榜。

每个 KPI 或列表都能点击进入带筛选条件的问题工作台。

### 9.3 问题工作台

提供以下筛选：

- 数据周期/创建周。
- 来源：全部、班牛、新工单。
- 店铺。
- 产品名称、商家编码、商品 ID。
- 一级、二级、三级问题。
- 五大分类。
- 统计状态：已纳入、可剔除、待归类。
- 仓库。
- 关键词。

表格至少显示：

- 工单/问题标识。
- 来源和来源工单 ID。
- 工单创建/更新时间。
- 产品、商家编码、商品 ID、SKU。
- 订单号/子订单号。
- 一级/二级/三级问题。
- 经营统计状态。
- 仓库和物流状态。
- 售后金额/退款金额（没有值显示 `—`）。
- 同步批次和证据状态。

点击一行打开右侧详情抽屉，详情分为：业务信息、问题分类、商品/订单、来源证据、同步运行、原始字段摘要。原始 JSON 默认折叠，不要在列表中直接展示大段 JSON。

### 9.4 产品周报

- 默认选择上一个完整周。
- 可以切换最近五个完整周。
- 按售后创建周统计经营异常问题，并按问题数降序。
- 显示产品名称、完整商家编码、关联商品 ID 数、当周问题数、前一周问题数、变化值。
- 缺少商家编码的记录单独显示“待匹配”，计入总量但不进入产品排名。
- 产品名称只作为展示文本，不作为聚合主键。

### 9.5 仓库分析

- 显示仓库问题数、订单数、仓库问题率、较前期变化。
- 显示仓库编码、仓库名称、来源和映射状态。
- 未完成映射时显示“待映射”，不使用全店订单作为兜底分母。
- 支持下钻到问题工作台并自动带入仓库筛选。

### 9.6 同步与数据质量

这是本次重构新增的核心页面，必须优先实现。

页面包含：

- 三个数据源卡片：最新同步时间、覆盖窗口、读取数、写入数、当前状态。
- 当前发布数据集：版本、发布时间、覆盖起止、来源构成。
- 同步运行列表：任务、来源、触发方式、窗口、状态、耗时、读写行数。
- 质量检查：分页完整性、重复身份、来源记录消失、交界对账、字段覆盖、订单水位、新鲜度。
- 失败任务详情：错误摘要、失败页/失败工单、是否可安全重试、建议恢复动作。
- 每笔工单证据入口：从运行列表跳转到具体来源证据。

状态必须区分：成功、部分成功、失败、未知、等待人工确认、数据已滞后。

### 9.7 规则设置

- 只有 admin 显示编辑能力，viewer 只读。
- 显示五大问题分类和可剔除规则的启用状态、说明、最后修改人、最后修改时间。
- 修改前提示“会影响首页、产品、仓库和趋势统计”。
- 保存后生成规则版本，并要求重新计算/发布业务数据集；不能静默改变历史结果。

## 10. 页面状态和错误处理

v0 必须设计并展示以下状态，而不是只做成功态：

- 首次加载：骨架屏。
- 无数据：说明数据窗口和可能原因。
- 数据已滞后：显示最后成功时间和滞后小时数。
- 部分成功：显示已覆盖范围、未覆盖范围和受影响指标。
- 数据集未发布：禁止显示看似正常的 0，改为“等待数据发布”。
- 未知副作用：显示“需要人工核对”，不提供无脑重试按钮。
- 无权访问：说明当前角色和所需角色。
- 网络错误/API 500：保留当前筛选条件，提供安全刷新。
- 分母缺失：指标显示 `—`，并说明缺失的订单水位或映射原因。

## 11. 安全、审计和可观测性

- 沿用公司网关注入的员工身份；Hono 侧必须验证用户 ID、显示名和角色，不信任前端传入的角色。
- 业务 API、管理 API 和内部任务 API 分开鉴权。
- 密码、JWT、Cookie、API Key、原始授权头不能写入日志或证据页面。
- 结构化日志至少包含 `request_id`、`user_id`、`source_system`、`sync_run_id`、`dataset_version`、状态、耗时和错误码。
- 原始数据和证据访问必须有审计日志。
- 每笔工单保留来源证据，但页面默认只展示脱敏后的摘要；必要时管理员才能查看原始字段。
- 数据集发布必须是原子切换：新版本未通过检查时，旧版本继续可读。
- 所有同步任务、补数和规则变更必须能够回答“谁、何时、从哪里、读取了什么、写入了什么、结果如何”。

## 12. v0 必须完成的最小范围

为了满足下周一交付，v0 只要求一个可演示的完整闭环：

1. Next.js 前端壳和上述导航。
2. Hono.js API 项目/接口契约，至少实现 health、overview、issues、products/weekly、warehouses、data-status、sync/runs。
3. PostgreSQL 最小表结构：同步运行、来源记录、证据、统一工单/商品行/问题事实、数据集版本、质量检查。
4. 以真实字段结构为基础的验收数据或受控样例数据，不能使用与业务无关的随机大屏数字。
5. 首页、问题工作台、产品周报、同步与数据质量四个页面能完整展示加载、成功、空数据、滞后和失败状态。
6. 当前周补数预演结果可以被记录；正式补数和生产切换必须另行验证，不在 v0 中伪装成已完成。
7. 每个问题行可以从页面追溯到来源和同步批次。

以下内容不阻塞 v0 页面演示：复杂 BI、自定义报表编辑器、消息队列、Redis、实时秒级更新、自动化业务处置、客服工单分派、移动端原生应用。

## 13. 验收标准

### 功能验收

- 可以从首页进入问题工作台、产品周报、仓库分析和数据质量页面。
- 页面筛选条件能写入 URL，刷新后可以复现。
- 页面只通过 Hono API 读取数据，不直接读数据库或源接口。
- 所有列表支持服务端分页，并返回总数和数据集版本。
- 任意一笔问题/工单都能查看来源系统、来源 ID、同步运行和证据摘要。
- 班牛、新工单和外部数据库在页面上可区分，并能查看来源构成。
- 当前周和上一周的补数结果可以按批次查看，交界周可以查看对账差异。
- 同步失败、数据滞后、质量未通过和分母缺失时，页面不会把未知结果显示成正常 0。

### 数据验收

- 同一来源重复同步不会产生重复业务记录。
- 每个已发布数据集都有同步批次、覆盖范围、质量检查和发布时间。
- 页面显示的售后总量、经营异常量、产品周报和问题明细可以相互对账。
- 全量问题 = 已纳入 + 可剔除 + 待归类。
- 产品排名合计与已匹配的经营异常问题一致，待匹配数量单独展示。
- 缺订单分母、缺仓库映射、缺商品编码时保留未知状态，不使用猜测值。
- 来源交界周输出班牛、新工单、重叠、缺失和疑似重复的对账结果。

### 工程验收

- Hono API 有 TypeScript 类型、参数校验、错误码和最小测试。
- PostgreSQL 迁移可重复执行，关键业务键和唯一约束明确。
- 同步任务有 dry-run、运行状态、结构化日志和失败重试边界。
- 前端有 loading、empty、stale、partial、error、unauthorized 六类状态。
- 新架构不新增 MySQL 依赖，不把旧 Next.js Route Handler 作为长期兼容层；迁移完成后以 Hono API 为唯一页面数据入口。

## 14. 待确认事项（不得由 v0 自行猜测）

以下问题会影响数据和页面，不应在实现中偷偷决定：

1. 班牛与新工单的正式交界时间 `cutover_at` 是什么？按自然日还是精确到时间？
2. 三个数据源的真实更新时间和可接受延迟分别是多少？哪些是日更，哪些是周更？
3. “周一 15:00 前完成”针对哪个时区、哪个数据窗口和哪个数据集？
4. 公司服务器外部数据库中，光电通及其他来源的实际数据库地址、表、只读账号和字段契约是什么？
5. 新工单 API 的认证、分页、稳定 ID、删除/修改语义和完整性校验方式是什么？
6. 班牛历史需要补到哪一天？首页五周、产品周报五周和比较周期是否全部覆盖？
7. 跨来源疑似重复由谁审核？审核结果是合并、保留两条还是标记无效？
8. 业务表中哪些字段需要允许管理员修改，哪些字段只能从来源同步？
9. 是否需要在 v0 中展示金额、退款、处理方式、凭证、任务状态、执行人和 SLA？这些字段目前部分缺失，不能在没有规则时伪造页面能力。
10. autorpc 是否作为正式采集调度中心？Hono、autorpc 和 launchd 的任务责任边界需要最终确认。
