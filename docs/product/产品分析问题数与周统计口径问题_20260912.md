# 产品分析“问题数”与周统计口径问题

记录日期：2026-09-12
状态：已在 0.6.0 修复并于 0.6.1 分类切换后再次完成生产对账。
涉及页面：产品售后分析 `/aftersales/products`。

## 1. 反馈与结论

用户提供的聊天截图中，反馈方指出“问题数对不上”，希望展示对应周的条数，并按该数量降序，以便集中查看真正有问题量的商品。

当前本地代码可以确认：左侧“问题数”取展示范围内最后一周，右侧周明细却从最早一周开始；排序优先看预警等级；商品列表覆盖整个展示窗口。这些设计与反馈方希望按指定周查看数量排名的需求不一致。

**已确认存在口径表达和排序问题，尚不能认定截图中的原始数量计算错误。** 截图对应的线上版本、数据快照、原始售后记录与实际分母匹配结果均未逐条核验。

截图中的聊天内容作为问题证据，不视为已经确认的开发方案。本文仅记录问题、建议及验收条件，不改变现有业务口径。

## 2. 问题清单

| 编号 | 问题 | 状态 | 影响 |
| --- | --- | --- | --- |
| P-01 | 左侧“问题数”没有日期，实际对应最后一周；右侧从最早周开始 | 已确认本地实现 | 容易将不同周的数据当成同一口径比较 |
| P-02 | 排序先看预警等级，再看最后一周问题数 | 已确认本地实现 | 不满足按所选周问题数全局降序的需求 |
| P-03 | 周归属按订单付款时间，可能与业务按售后创建时间对账的习惯不同 | 实现已确认，业务意图待确认 | 改表头或排序后仍可能对不上账 |
| P-04 | 列表按整个窗口内的异常记录归组，未排除当期为零的商品 | 已确认本地实现 | 列表数量不能代表当期有问题的商品数 |
| P-05 | 问题数按售后记录行计数，且仅包含纳入经营异常的类别 | 已确认本地实现，生产记录待核实 | 不能直接等同于全部售后工单数或去重订单数 |
| P-06 | 不同规格独立成行，但分母可能匹配同一基础编码 | 存在该代码路径，截图是否命中待确认 | 可能影响商品售后率及预警可信度 |

## 3. 具体分析

### P-01：两个红框对应不同周

当前完整周模式默认展示最近 5 个已结束自然周，周日开始、周六结束。周明细按时间从早到晚排列。

| 字段 | 当前含义 |
| --- | --- |
| 左侧问题数、订单数、销量、售后率 | 展示范围内最后一周的对应指标 |
| 左侧变化 | 最后一周相对前一周的售后率差，计算单位为百分点 |
| 右侧 `0802–0808` | 8 月 2 日至 8 月 8 日的对应指标 |

截图第一行左侧为 22，`0802–0808` 为 7，二者不要求相等。22 也不是各周合计，因为截图可见的前三周已经是 `7 + 7 + 21 = 35`。截图未展示最右侧最后一周，不能据此验证 22 是否与其一致。

检查依据：[当期指标计算](../../src/modules/analytics/metrics.ts)、[周窗口生成](../../src/modules/analytics/date-windows.ts)、[表格字段展示](../../src/components/virtual-summary-table.tsx)。

### P-02：实际排序与数量排名目标不一致

产品列表先按 `alertRank` 降序，同等级内再按最后一周问题数降序。因此，数量较少但售后率上升的商品，可能排在数量较多但售后率下降的商品之前。

如果分析周选择 `0802–0808`，仅截图可见的这几行应按 `84 → 58 → 15 → 10 → 7 → 2 → 0` 排列。这只是截图样本的排序，不代表全量商品排名。

检查依据：[产品归组及排序](../../src/modules/analytics/service.ts)中的 `productRowsByCode`。

### P-03：付款周与售后发生周是两种不同口径

SQL 使用 `wdt_pay_time` 划分周窗口。同步脚本将来源付款时间写入该字段。完整周模式没有按各周结束时间截断售后创建时间，因此后续同步到的售后会归回原付款周。

示例：8 月 5 日付款，8 月 20 日创建售后。当前完整周模式计入 `0802–0808`；若按售后创建周统计，则计入 `0816–0822`。

| 口径 | 回答的问题 |
| --- | --- |
| 订单付款周 | 这一周卖出的订单，后来产生了多少售后问题？ |
| 售后创建周 | 这一周新产生了多少售后问题？ |

付款周已经结束不代表售后已充分出现。较新的付款周仍可能持续补入问题，不能仅凭数量较低判断已经改善。本周同进度模式还附加售后创建时间截止条件，不能将两种模式视为只更换日期标签。

如果改为按售后创建周统计，不能直接沿用“该周付款订单数”作为同一批订单的售后率分母，需同时明确售后率的定义。

检查依据：[统计 SQL](../../src/modules/analytics/repository.ts)中的 `placeholders`、`issueScope`；[班牛同步映射](../../scripts/banniu_aftersales_sync.py)中的 `normalize`。

### P-04：488 行不等于当周有 488 个商品产生问题

产品从整个展示窗口内的经营异常记录中按完整商家编码归组，没有增加“所选周问题数大于 0”的条件。因此，历史周有问题而当期没有问题的商品仍可能出现。

`A*3` 与 `A*6` 会分成两行，即使业务上认为它们属于同款不同装数。名称相似不能作为合并依据，需要明确产品与规格的归组规则。

截图中零值商品数量、同款不同规格数量均待生产数据核实。检查依据：[产品归组](../../src/modules/analytics/service.ts)、[列表筛选](../../src/modules/analytics/filters.ts)、[产品页面](../../app/products/page.tsx)。

### P-05：计数单位与纳入范围需要明确

当前 SQL 对售后记录行累加；同步以“班牛任务 ID + 子商品键”生成业务键并执行更新写入。一个任务涉及多个商品时，可能贡献多条计数，不能直接当作一张工单。

产品分析仅纳入五大分类中未命中可剔除规则的记录。可剔除或待归类记录不进入产品汇总，因此也不等于全量售后数量。

同一商品同一周对账时，必须同时统一时间字段、商品编码、问题类别范围、计数单位和数据截止时间。生产唯一约束、重复记录及来源漏数尚未核验。

检查依据：[计数 SQL](../../src/modules/analytics/repository.ts)、[分类规则](../../src/modules/problem-rules/classifier.ts)、[经营异常过滤](../../src/modules/analytics/service.ts)、[同步业务键](../../scripts/banniu_aftersales_sync.py)。

### P-06：相同订单数和销量需核查实际分母来源

截图部分不同行的订单数、销量完全相同。代码允许完整商家编码匹配不到时，去掉尾部 `*数量` 后匹配基础编码，组合编码还存在拆分匹配路径。

如果不同规格的问题数分别统计，却使用同一基础编码的订单数，分子与分母的商品范围可能不一致。相同数值本身不足以证明错误，也不能证明截图中的行命中了该路径。

核查时需记录每行实际命中的编码、精确或基础编码匹配方式、分母覆盖商品范围，并确认其与分子一致。检查依据：[分母匹配](../../src/modules/analytics/product-orders.ts)中的 `orderSeries`。

## 4. 待确认的业务决定

1. “对应周”指订单付款周，还是售后创建周？这是实施前必须明确的决定。
2. “条数”指经营异常商品记录数、去重售后工单数，还是去重订单数？是否包含全部问题类别？
3. 一行继续代表完整商家编码，还是需要按已维护的产品与规格关系归并？
4. 默认查看哪一周？是否认可默认只展示该周问题数大于 0 的商品？

## 5. 建议修正范围

以下为建议，尚未确认为实施需求：

- 用明确的分析周选择统一整张表，并展示日期归属口径、计数单位和数据更新时间。
- 左侧改为“所选周问题数”；订单数、销量、售后率及变化同步跟随所选周，不混用最后一周。
- 默认按所选周问题数全局降序；预警保留为提示。并列时使用稳定的商品编码顺序。
- 默认仅显示所选周问题数大于 0 的商品，提供包含零值商品的开关，并注明商品数量的统计范围。
- 保留历史周明细并突出所选周，使横向比较能直接对应。
- 页面、下钻明细、分页接口和 Excel 导出共享同一筛选、周期及排序定义。
- 经数据核实后处理分母范围问题；不根据截图直接合并编码或改写历史数据。

本问题不包含工单流程、负责人、SLA 或其他 CRM 能力扩建。

## 6. 验收标准

| 验收项 | 通过条件 |
| --- | --- |
| 周指标一致 | 同一商品左侧所选周问题数与对应周明细完全一致，其他当期指标同样一致 |
| 排序正确 | 全量结果按所选周问题数降序，预警等级不改变数量排名；分页追加后仍保持顺序 |
| 商品数量准确 | 默认结果仅包含所选周问题数大于 0 的商品，显示总数与实际筛选结果一致 |
| 原始记录可对账 | 选取高问题量、当期零值、跨周创建售后的商品样本，按确认口径复算并与页面一致 |
| 计数单位明确 | 同一工单含多个商品、同一订单多次售后、重复同步等样本均符合确认的计数定义 |
| 分母范围正确 | 相同分母或基础编码匹配样本能够解释来源，分子与分母覆盖同一商品范围；无可靠分母时不展示可计算售后率 |
| 跨入口一致 | 页面、下钻、分页和导出使用同一周及问题范围，汇总数量可以相互核对 |
| 时间含义可理解 | 用户能区分付款周与售后创建周，知道付款周历史数量可能随迟到售后补入 |
