# 售后看板改版复盘与修正计划

## 一、结论

当前版本技术重构基本成功，但产品迁移不合格。

问题不在于新版页面不好看，而在于改造时同时更换了技术、信息架构和用户工作方式。旧版售后人员以“整体大表—筛选—对账—导出”为核心，新版却变成“总览卡片—排行—分页面查看”，导致核心工作台被弱化。

> 新版更适合管理层快速看趋势，但降低了售后人员查数、对账和导出的效率。

下一阶段停止扩展新的管理功能，先完成旧版核心能力的等价迁移。

## 二、已确认的能力差异

旧版核心能力：

- 一级问题分类汇总。
- 重点问题大表。
- 商品、问题分类、商家编码精确查询。
- 近 5 周问题数、售后率及环比横向对比。
- 商品和仓库专项视图。
- 完整周、本周同进度两种口径。
- 类别、明细、商品、仓库四类 Excel 导出。
- 导出全部筛选结果，不受页面显示条数限制。

依据：归档中的 `crm_server.py` 旧版页面与导出实现，以及 `archive/legacy-python-dashboard/docs/CRM全表Excel导出灰度运维_20260730.md`。

新版已经完成响应式布局、经营总览、问题明细、商品分析、仓库分析、周期切换、虚拟滚动、数据健康检查和统一登录，但存在以下业务回退：

- 全量大表入口不突出。
- 总览只展示摘要和少量风险对象。
- 商品页只展示风险最高的 50 项。
- 近 5 周具体数字被趋势图替代。
- Excel、CSV 导出尚未迁移。
- 部分指标术语不符合售后人员习惯。

## 三、根本问题

1. 把管理看板当成了售后工作台。管理层需要摘要，售后人员需要逐行查看、横向比较、复制、筛选和导出。
2. 技术升级和产品重设计同时发生。正确顺序应先完成能力等价，再逐步增强。
3. 虚拟表格只解决了 DOM 性能，没有解决入口、信息密度、周数值和导出等可用性问题。
4. 导出是对账、跨部门沟通、商品复盘、仓库追踪和周报的核心业务能力。

## 四、目标产品结构

新版首页采用“总览 + 工作台”结构：

```text
数据状态与分析周期
        ↓
核心指标与重点预警
        ↓
一级问题分类汇总
        ↓
全量售后问题大表
        ↓
商品、仓库专项分析
```

全量大表继续使用虚拟滚动。筛选器服务于大表，不能替代大表。

大表恢复以下字段：

- 商家编码、抖店商品 ID、商品名称。
- 一级问题、二级问题、问题大类。
- 当期问题数、当期订单数、当期售后率。
- 较上期变化，统一使用 `%` 显示。
- 近 5 周问题数、近 5 周售后率。
- 预警状态。

桌面端使用完整表格，手机端继续使用卡片式布局。

## 五、Excel 方案

每个分析页面提供“导出当前结果”，首页提供“导出完整经营分析”。完整工作簿包含：

1. 一级类别汇总。
2. 售后问题明细。
3. 商品分析。
4. 仓库分析。

导出规则：

- 支持完整周和本周同进度。
- 保留关键词、问题分类、商家编码等筛选条件。
- 导出全部匹配结果，不受页面显示数量和虚拟滚动影响。
- 商家编码、抖店商品 ID 强制按文本写入。
- 记录分析周期、数据更新时间和订单截止日期。
- 页面与导出共用同一套查询和计算逻辑。

## 六、实施顺序

### P0：恢复产品等价能力

- 首页恢复全量售后大表。
- 恢复近 5 周具体数值。
- 增加四类 Excel 导出和完整经营分析工作簿。
- 商品页取消只显示 50 项的硬限制。
- `pp` 改为 `%`，“预计外问题”改为“超出预期问题数”。
- 保留响应式和虚拟滚动能力。

### P1：售后操作体验

- 固定表头和关键字段列。
- 增加列显示控制。
- 商品、仓库排行可下钻到已筛选大表。
- 显示当前结果数、页面加载范围和 Excel 导出范围。
- 增加简短使用引导和周期口径说明。

### P2：数据与性能优化

- 将筛选条件下沉到服务端查询，减少 RSC 页面响应体。
- 大规模导出采用服务端流式生成。
- 记录导出任务耗时、行数和失败原因。
- 继续使用 MySQL 汇总表，不因此引入 Redis。
- 增加页面与 Excel 一致性自动测试。

## 七、验收标准

- 旧版核心字段全部可见。
- 全量大表可以连续滚动、筛选和精确查询。
- 完整周与本周同进度均可使用。
- 四类 Excel 和完整工作簿均可打开。
- Excel 行数等于完整筛选结果。
- 页面与 Excel 的指标、周期和口径一致。
- 商品编码不会被 Excel 错误转换。
- 桌面、平板、手机没有横向页面溢出。
- 售后人员无需阅读技术文档即可完成查数、定位和导出。
- 验收完成前保留旧版回滚能力，不清理旧服务。

## 八、目标

> 保留新版技术架构、响应式设计和性能优势，完整恢复旧版大表、数值对比和 Excel 导出工作流。

## 九、0.2.2 实施记录

P0、P1 和当前范围内的 P2 已在本地完成：

- 首页和问题明细均恢复全量问题工作台，桌面端为固定关键列的虚拟表格，窄屏为卡片布局。
- 恢复近 5 周问题数和售后率；变化统一使用 `%`，异常增量统一称为“超出预期问题数”。
- 类别、明细、商品、仓库和完整经营分析均可导出 Excel；完整工作簿包含 4 个工作表。
- 商品和仓库页面展示全部结果，并可下钻到带筛选条件的问题工作台。
- 工作台首屏只下发 160 行，连续滚动时每批按需读取最多 240 行；商品页首屏只下发 120 项，继续滚动时每批读取最多 200 项；筛选和 Excel 仍使用全部匹配结果。
- Excel 使用服务端流式生成，记录导出视图、周期、行数、耗时、用户和失败原因。
- 页面筛选和 Excel 共用过滤与指标逻辑，并以自动化测试验证行数、口径、文本编码和公式注入保护。
- 数据层继续使用 MySQL 汇总表和 Next.js 服务端缓存，没有引入 Redis。
- 商品标识拆分为“售后商品ID（班牛）”和“抖店商品ID（已确认）”；页面保持原始字符串，Excel 两列均使用文本格式，避免长数字被格式化或转为科学计数法。

验收结果：6 个测试文件共 16 项通过，TypeScript、ESLint 和生产构建通过；390×844 视口页面宽度无溢出，移动端工作台采用单列筛选和双列数据卡片；2,400 行本地验收数据仅渲染约 14 至 26 行可见节点。真实生产数据下，首页响应约 233 KB，商品页响应由约 1.15 MB 降至约 145 KB；页面 2,418 条问题组合、1,197 个商品与完整 Excel 结果范围一致。商品 ID 实际长度覆盖 10 至 19 位，2,409 条明细保留班牛原始 ID，566 条展示已确认抖店 ID，接口与 Excel 均保持字符串原值。

## 十、0.3.0 数据质量修正

- 修复侧栏 Logo 图片优化器回源被员工鉴权拦截的问题。
- 将“商品订单数据缺失”和“真实 0 订单”拆成两种状态：只有商品日汇总水位完整覆盖分析窗口时，缺行才认定为 0。
- 商品汇总滞后时，只对一条商家编码明确对应一个商品 ID 的记录使用商家订单回填；一对多关系不做推断，页面显示“—”，Excel 留空。
- 班牛问题明细改为按商品 ID 分组，避免同一商家编码下多个商品被合并。
- 页面、Excel 和 `/readyz` 同时公开商品订单截止日期与部分可用状态。
