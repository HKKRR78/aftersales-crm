# 售后看板数据策略

## 结论

继续使用 MySQL 8，暂不引入 Redis、消息队列或新的数据库。当前首要问题是批处理链路耦合、数据完整性判定和数据水位，不是页面缓存吞吐。

## 本次生产验证暴露的问题

1. 班牛同步、仓库映射、周汇总和日汇总串行执行。班牛一条超长子订单键失败后，后续两个独立订单汇总也停止执行。
2. 班牛脚本按页提交。失败前写入的数据会更新 `api_synced_at`，因此“最新同步时间”不能证明整个批次完整。
3. 周汇总读取 `ods_wdt_stock_out_api_line`，日汇总读取 `ods_wdt_stock_out`，两个来源的更新节奏不同。
4. 日汇总可以生成“存在但订单数为零”的日期。只检查日期行是否存在会产生假健康。
5. 浏览器虚拟表格减少了 DOM 行数，但真实明细页响应仍约 1.15MB。数据继续增长后需要改为服务端分段加载。

## 数据分层

### 原始采集层

- 保留班牛历史、新工单、WDT 和抖店来源数据。
- 每次采集必须有唯一批次号、来源窗口、读取行数、写入行数和完成状态。
- 只有完成全部分页核对的批次才能标记为 `complete`。

### 标准事实层

- `ods_crm_aftersales` 保存来源分离的统一售后事实；`ods_crm_ticket_raw` 保存新工单原始 JSON。
- `etl_crm_ticket_batches` 保存新工单覆盖范围、完整性核对和成功发布水位。
- 商品、店铺、仓库和订单键在写入前完成长度、类型和唯一性校验。
- 超长来源键使用稳定 SHA-256 表示，避免因单条异常中断整批。

### 分析汇总层

- `dws_crm_order_weekly` 和 `dws_crm_order_daily` 继续作为页面分母。
- 周、日汇总独立调度，不因班牛接口失败而停止。
- 页面请求只读汇总表，不扫描订单源表。
- 周、日汇总应逐步统一到同一个经过验证的订单事实来源。

### 产品读取层

- 完整周视图只读取已经完成的周汇总。
- 本周同进度使用最近一个订单数大于零的完整日期作为共同水位。
- 页面必须显示订单水位；超过允许滞后天数时停止服务并返回 `503`。
- 未来明细表采用服务端分段加载加浏览器虚拟滚动，避免把全部行序列化到首屏。

## 最小治理表

后续新增三类元数据即可，不需要引入额外基础设施：

- `etl_job_runs`：任务名称、运行键、状态、时间范围、读写行数、开始结束时间和错误码。
- `analytics_dataset_versions`：一组可供页面读取的售后批次、订单水位和发布时间。
- `analytics_quality_checks`：分页完整性、行数变化、日期覆盖、零订单异常和来源滞后检查。

页面只读取最近一个通过全部必要质量检查的已发布版本。新任务失败时继续保留上一个完整版本，并明确显示数据水位和滞后状态。

## 为什么现在不使用 Redis

Redis 不能修复采集分页失败、订单源表滞后、汇总链路中断或错误水位。当前数据量下，MySQL 汇总查询已能在百毫秒级完成。引入 Redis 反而增加缓存一致性、持久化、容量和恢复边界。

只有出现以下需求时再重新评估：

- 多台 Web 实例需要共享高频热点缓存。
- 出现秒级事件消费或高频实时队列。
- 需要跨实例分布式限流或短租约协调。
- MySQL 物化汇总仍无法满足经过实测的延迟目标。

## 落地顺序

1. 将现有四步脚本改为可独立成功、独立失败、独立补跑的任务。
2. 建立 `etl_job_runs`，记录每次运行的完整结果。
3. 统一周、日订单事实来源并建立必要索引。
4. 增加数据版本发布和质量检查。
5. 将大明细改为服务端分段加载与虚拟滚动结合。
6. 有实测瓶颈后再评估 Redis，不提前引入。
